I dug much deeper, including the source tree, compiler diagnostics, crypto test vectors, and the TLS state machine. The good news is that the core primitives are substantially better than I initially gave them credit for. I also found several real bugs that I would fix before treating this as security-grade code.

I would **not ship this yet**.

The most important finding is a **remote-triggerable out-of-bounds read in the TLS ServerHello path**.

---

# 1. Critical: ServerHello length can cause an out-of-bounds read

This is the most concrete bug I found.

You have:

```c
uint8_t sh_body[4096];
uint32_t sh_bl;
```

Then:

```c
st->sh_bl = hs_bl;
for (uint32_t i = 0; i < hs_bl && i < sizeof(st->sh_body); i++)
    st->sh_body[i] = st->rec_buf[5 + 4 + i];
```

The copy is bounded to 4096.

But `st->sh_bl` remains the original attacker-controlled `hs_bl`.

Immediately afterwards:

```c
tls_transcript_update_msg(&snap,
                          TLS_HS_SERVER_HELLO,
                          st->sh_body,
                          st->sh_bl);
```

So if the server sends a ServerHello body larger than 4096 bytes, the transcript code reads past `st->sh_body`.

The same problem exists later in:

```c
transcript_st()
```

and:

```c
transcript_of()
```

### Impact

Remote server-controlled memory read.

Depending on compilation and surrounding memory layout:

* crash
* information leakage through subsequent cryptographic processing
* undefined behavior
* potentially exploitable memory corruption if the resulting behavior interacts with other bugs

The attacker controls ServerHello before server authentication has happened.

### Fix

Reject it before copying:

```c
if (hs_bl > sizeof(st->sh_body)) {
    st->fail_reason = TLS_FAIL_PROTO;
    return TLS_STEP_ERR;
}
memcpy(st->sh_body, st->rec_buf + 5 + 4, hs_bl);
st->sh_bl = hs_bl;
```

Do this everywhere a bounded copy establishes a length field.

**Severity: High/Critical.**

# 2. Critical API bug: `send_aead()` has integer-overflow paths

This is another genuine memory-safety problem.

You have:

```c
if (pt_len + 1 > sizeof(inner)) return -1;
memcpy(inner, pt, pt_len);
```

`pt_len` is `uint32_t`.

For:

```text
pt_len = UINT32_MAX
```

then:

```text
pt_len + 1 == 0
```

The check passes.

Then:

```c
memcpy(inner, pt, pt_len);
```

attempts an enormous copy into a ~18 KB buffer.

You also have:

```c
uint32_t ct_len = pt_len + 1 + 16;
```

which can overflow too.

### Fix

Never perform the addition before checking:

```c
if (pt_len >= sizeof(inner))
    return -1;
```

Then:

```c
uint32_t ct_len = pt_len + 1 + 16;
```

is safe because `pt_len` is now bounded.

This matters because `request_len` comes directly from the caller.

**Severity: High for a library/API, lower if the caller is absolutely trusted and length-bounded elsewhere.**

# 3. High: output-buffer length arithmetic can wrap

You have:

```c
if (st->out_len + pl > st->out_cap)
```

Again, unsigned addition.

An attacker could theoretically make `out_len + pl` wrap after enough application data.

Then:

```c
memcpy(st->out + st->out_len, pt, pl);
```

can write beyond the caller's buffer.

The practical requirement is a multi-gigabyte response, so this is not an easy exploit, but the check is objectively wrong.

### Fix

Use subtraction:

```c
if (pl > st->out_cap - st->out_len)
    fail();
```

provided `st->out_len <= st->out_cap` is maintained as an invariant.

Or use checked addition.

**Severity: Medium.**

# 4. High architectural problem: the RNG is not actually a cryptographic entropy subsystem

This concerns me more than most of the parser issues.

The header says:

```c
// Seeded from RDTSC + IRQ jitter + e1000 MAC.
```

The MAC address is not entropy.

A MAC address is effectively public.

Likewise, "IRQ jitter" and RDTSC timing can contribute entropy, but only if you have a carefully designed entropy-collection and conditioning system.

Your readiness criterion is:

```c
if (rng_bytes_generated >= 32 * 32)
    rng_ready = 1;
```

That means:

> 32 calls to `rand_stir()` are enough.

It does **not** mean:

> 1024 bits of entropy have been collected.

Those are radically different statements.

For example, this sequence:

```c
rand_stir(zeroes);
rand_stir(zeroes);
...
```

32 times results in a "ready" RNG with no entropy.

The same applies if your entropy source is highly predictable.

### More importantly

The RNG API accepts arbitrary caller-provided "entropy":

```c
void rand_stir(const uint8_t entropy[32]);
```

There is no source identification, entropy estimate, health test, startup test, or independent source requirement.

### What I'd do

For a kernel:

1. Obtain entropy from a real hardware source if available.
2. Mix multiple independent sources.
3. Use a cryptographic DRBG such as ChaCha20-based DRBG.
4. Maintain an explicit entropy-initialized state.
5. Don't declare readiness based on number of samples.
6. Reseed periodically.
7. Reseed after VM snapshot/restore if relevant.
8. Ensure fork/process duplication isn't possible in host mode.
9. Make concurrent access serialized.
10. Fail closed if entropy initialization hasn't completed.

The current construction can be made useful, but **the entropy source and initialization protocol are just as important as the ChaCha20 state machine.**

**Severity: Critical if the claimed kernel entropy sources are the actual production design.**

# 5. High: host RNG has a predictable fallback

The non-kernel path does:

```c
/dev/urandom
```

but falls back to:

```c
time(NULL)
getpid()
```

plus xorshift.

That's not cryptographically secure.

You correctly removed the fixed seed, but the fallback remains predictable.

If the host implementation is genuinely test-only, enforce that structurally.

For example:

```c
#ifdef TEST_ONLY
...
#else
#error "No cryptographic RNG implementation"
#endif
```

Or just fail if `/dev/urandom` isn't available.

Do not silently downgrade cryptographic randomness.

**Severity: High if host builds can ever become production builds.**

# 6. High: RNG is not concurrency-safe

These are global mutable variables:

```c
static uint8_t rng_key[32];
static uint8_t rng_nonce[12];
static uint32_t rng_counter;
static uint32_t rng_bytes_generated;
static int rng_ready;
```

There is no locking.

Two simultaneous users can race:

```text
A reads key
B reads key
A generates block
B generates block
A updates key
B updates key
```

That is not a valid DRBG state transition.

The same problem exists with:

* ticket cache
* pin cache
* `ec_ctx_ready`
* global clock
* host RNG state
* `g_last_fail_reason`

If this kernel is truly single-threaded and interrupts cannot call into these paths, document that as an invariant and enforce it.

Otherwise this needs synchronization.

**Severity: High in a preemptive/concurrent environment.**

# 7. High: TLS 1.3 record-size limit is wrong

You define:

```c
#define TLS_RECORD_MAX_PAYLOAD 18432
```

TLS 1.3's maximum ciphertext record is not 18 KiB.

The normal limits are approximately:

```text
plaintext fragment: 16384
ciphertext: 16384 + expansion
```

For ChaCha20-Poly1305, that means roughly:

```text
16384 + 1 content-type byte + 16 tag
```

not 18432.

Your implementation accepts substantially larger records.

This isn't immediately a cryptographic break, but it:

* violates the protocol
* increases resource consumption
* expands parser attack surface
* makes memory accounting less obvious

I'd use separate constants:

```c
TLS_PLAINTEXT_MAX = 16384
TLS_CIPHERTEXT_MAX = 16384 + 1 + 16
```

and enforce them by record type.

# 8. High: TLS sequence numbers can theoretically wrap

You do:

```c
(*seq)++;
```

TLS 1.3 requires terminating before sequence-number exhaustion.

After:

```text
2^64
```

records, the nonce repeats.

That's fantastically impractical, but cryptographic code should encode the invariant rather than rely on the universe ending first.

Use:

```c
if (*seq == UINT64_MAX)
    return -1;

...
(*seq)++;
```

Same for send and receive.

# 9. High: TLS handshake messages cannot span records

This is a major protocol implementation limitation.

In `RECV_HS`, you decrypt one record and then:

```c
parse_hs(pt + p, pl - p, ...)
```

If a handshake message is fragmented across TLS records, parsing fails.

TLS permits handshake messages to be fragmented across records.

Therefore a legitimate server can send:

```text
record 1: first 1000 bytes of Certificate
record 2: remainder of Certificate
```

and this client rejects it.

That's primarily interoperability/DoS, but the correct architecture needs a handshake-message reassembly buffer independent from the record buffer.

The same issue exists for large Certificate messages.

# 10. High: the X.509 chain builder is far too simplistic

The current model is essentially:

```text
leaf
  ↓
certificate[1]
  ↓
certificate[2]
  ↓
...
trusted SPKI
```

Real PKI path construction isn't necessarily linear.

You don't implement:

* alternate issuer selection
* alternate chains
* AuthorityKeyIdentifier
* SubjectKeyIdentifier
* trust-anchor constraints
* path-building search
* policy processing
* name constraints processing
* policy mapping
* inhibit-any-policy
* explicit-policy constraints
* revocation checking

The biggest consequence is interoperability, but some are security properties.

Your embedded root store only contains 14 roots, which means many perfectly legitimate websites will fail.

That's okay if this is intentionally a tiny trust store. It is not okay if this is intended to be a general browser TLS stack.

# 11. High: no certificate revocation checking

You explicitly don't validate the OCSP response.

You even have:

```c
// content is NOT validated
```

So a revoked certificate remains trusted until it expires.

For a general browser this is a serious limitation.

There are arguments for soft-fail revocation, but "no revocation mechanism at all" is different.

At minimum I'd document the security model as:

> Compromised/revoked certificates remain trusted until expiration.

# 12. High: `verify_host` is a dangerous authentication bypass API

This field is public:

```c
const char* verify_host;
```

and the code deliberately permits:

```c
const char* vhost =
    st->verify_host ? st->verify_host : st->host;
```

This means the TLS state can be configured to send:

```text

```

while verifying:


A better design:

```c
#ifdef TESTING
...
#endif
```

# 13. Medium/High: ECDSA accepts noncanonical INTEGER encodings

In `ec_verify()`:

```c
while (rl > 1 && rb[0] == 0) { rb++; rl--; }
```

and same for `s`.

You don't enforce the ASN.1 INTEGER sign rules.

For ECDSA DER signatures, you should reject:

* negative INTEGERs
* unnecessary leading zeros
* zero
* values >= order

You currently reduce:

```c
scalar_from_be(...)
```

modulo `n`.

Then you only test:

```c
if (cmp_fe(r, c->nd.m, c->nl) == 0)
```

rather than:

```text
r >= n
```

So:

```text
r = n + valid_r
```

can become `valid_r`.

Same for `s`.

This doesn't immediately provide a forgery because the attacker still needs a mathematically valid signature, but it violates strict ECDSA encoding and makes the verifier accept signatures that a strict implementation rejects.

Fix with:

```c
if (r == 0 || r >= n) reject;
if (s == 0 || s >= n) reject;
```

before reduction.

# 14. Medium: EC public-key coordinates are reduced instead of rejected

You decode:

```c
be_to_limbs(...)
fe_set_mont(...)
```

and then test the resulting value.

So a coordinate representing:

```text
x = p + x_valid
```

can be reduced modulo `p` and become a valid point.

SEC1 encoding requires the coordinates themselves to be in range.

You should explicitly check:

```c
x < p
y < p
```

before converting to Montgomery form.

Again, this is generally an attacker-controlled malformed certificate that must also be signed by a CA, so it isn't an obvious remote forgery, but it is a verifier correctness hole.

# 15. Medium: RSA public-key validation is incomplete

You correctly check that the modulus is odd.

But you don't properly validate the public exponent.

Things that should be rejected:

```text
e = 0
e = 1
e = 2
even e
```

The usual RSA public exponent constraints should be enforced.

You also don't strictly establish the modulus bit length.

For the TLS certificate path I'd enforce at least:

```text
n >= 2048 bits
e >= 3
e odd
```

and preferably explicitly accept only known-safe exponent ranges.

# 16. Medium: RSA-PSS verifier doesn't enforce the unused top bit

You do:

```c
db[0] &= 0x7F;
```

but don't first reject a set top bit in the encoded message.

PSS has an `emBits` constraint.

The implementation should verify the unused high bits are zero before masking/processing them.

Again, this is not an obvious practical forgery by itself, but the verifier should implement the exact EMSA-PSS encoding rules.

# 17. Medium: X.509 INTEGER validation is too lax

`int_bytes()` does:

```c
while (len > 1 && p[0] == 0x00)
    p++, len--;
```

without validating that the original INTEGER was:

* positive
* minimally encoded
* nonzero where required

For RSA modulus/exponent parsing, malformed INTEGERs can therefore reach the crypto layer.

The DER parser should have a dedicated:

```c
der_read_positive_integer()
```

rather than generic raw INTEGER extraction.

# 18. Medium: AlgorithmIdentifier validation is incomplete

`parse_alg_id()` reads:

```text
SEQUENCE {
    algorithm OID,
    parameters ANY
}
```

but doesn't require the sequence to be completely consumed after the optional parameter.

Consequently malformed AlgorithmIdentifiers containing extra elements can be accepted.

Also, parameters are not consistently checked.

For example, RSA signature AlgorithmIdentifiers should have the expected NULL parameters where applicable, while ECDSA signature algorithms have different rules.

Strict parsers should validate each algorithm's complete expected encoding.

# 19. Medium: malformed extension BOOLEAN can be treated incorrectly

This:

```c
ext_critical = (inner.content_len == 1 &&
                inner.content[0] == 0xFF);
```

means a malformed BOOLEAN doesn't necessarily cause rejection.

For DER, BOOLEAN encoding is stricter than "one byte that happens to be FF".

If the BOOLEAN is present, validate:

```text
length == 1
value == 00 or FF
```

and reject malformed encodings.

# 28. Medium: TLS handshake state machine assumes too much

The server flight is hardcoded:

```text

Certificate
CertificateVerify
Finished
```

or:

```text

Finished
```

for PSK.

# 29. Medium: TLS record nonce construction is correct, but sequence lifecycle needs hardening

This:


is the correct TLS 1.3 XOR construction for a 96-bit IV.

* explicit sequence exhaustion handling
* zeroization on key change

The latter is currently implicit.

# 30. Medium: sensitive state isn't zeroized

This is a big deal for a kernel implementation.

`struct tls_state` contains:

```text
priv
hs_secret
c_hs_secret
s_hs_key
c_hs_key
s_ap_key
c_ap_key
c_fin_key

```

and remains in memory.

Likewise the ticket cache holds:


There is a `tls_ticket_clear()`, but normal connection completion doesn't erase secrets.

You should have something like:

```c
tls_state_wipe()
```

that securely clears sensitive fields before transitioning to DONE.

Be careful that the compiler doesn't optimize the clearing away. On freestanding code, implement an explicit secure zero routine with appropriate compiler barriers.

```text
    ↓
Certificate
    ↓
certificate chain
    ↓
hostname
    ↓
CertificateVerify
    ↓
Finished
    ↓
application data
```

You are not making the classic mistake of trusting the certificate without verifying `CertificateVerify`.

That is a major positive.

---

# 47. The PSK/resumption design is mostly sane

I looked specifically for the classic TLS 1.3 PSK mistakes.

You correctly:

* derive the resumption master after the handshake
* derive the PSK from the ticket nonce
* calculate the binder over the truncated ClientHello
* keep the PSK extension last
* always include ECDHE
* don't use 0-RTT application data
* reject a server selecting a non-existent identity
* skip Certificate/CertificateVerify only after PSK acceptance

That's considerably better than many homebrew TLS implementations.

The main weaknesses are ticket lifetime/clock semantics and cache management.

# 48. There is still a fundamental problem with the project philosophy

The source comments show an interesting pattern.

You have already fixed a lot of very specific bugs:

```text
#1 AEAD scratch overflow
#2 certificate clock
#4 CertificateVerify RSA algorithm
#5 plaintext alerts
#6 X.509 constraints
#7 HKDF label buffer
#8 host RNG
#9 root override
#10 RSA strength
#11 parsing/arithmetic issues
```

That's good.

But you're currently doing **patch-driven security** rather than **invariant-driven security**.

The next stage should be:

### Define invariants

For example:

**Every network-derived length:**

```text
0 <= length <= backing buffer
```

**Every cursor:**

```text
0 <= cursor <= enclosing_length
```

**Every cryptographic scalar:**

```text
1 <= scalar < group_order
```

**Every EC coordinate:**

```text
coordinate < field_prime
```

**Every RSA key:**

```text
n >= 2048 bits
n odd
e odd
e >= 3
```

**Every TLS record:**

```text
ciphertext_length <= protocol_max
```

**Every TLS sequence:**

```text
sequence < 2^64
```

**Every secret:**

```text
has explicit ownership and wipe lifecycle
```

Then make the code enforce those invariants mechanically.

That will find more bugs than another round of looking for individual mistakes.

## Bottom line

I would revise my original rating substantially.

**The crypto primitives are not the disaster area. The protocol glue, parsing, RNG architecture, and lifecycle management are.**

My current score:

**Cryptographic primitive implementation: 8.5/10**

**TLS protocol implementation: 6/10**

**X.509 implementation: 5/10**

**Memory-safety discipline: 5/10**

**RNG architecture: 4/10**

**Overall security readiness: 5.5/10**

The **ServerHello OOB read** is the first thing I'd fix. It is a concrete bug, not merely a standards-compliance complaint.

And after that, I would build a fuzz harness around **every externally reachable parser**, compile continuously with ASan/UBSan, and differential-test every primitive against a reference implementation. That will be much more valuable than manually finding the 43rd edge case in the source.
