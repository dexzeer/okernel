Yes. The latest revision is materially better. I re-read the new archive and also differential-tested the X25519 implementation against Python `cryptography` across 100 random cases.

**Updated rating: 7.5/10.**

The previous X25519 `fe_mul121665()` secret-dependent branch is gone, and the field arithmetic now matches an independent implementation on the tested vectors. I would still not sign off on this stack yet. I found several remaining holes, including two I would classify as security-relevant.

## 1. High: X25519 API still accepts an all-zero shared secret

You added:

```c
int shared_is_zero(const uint8_t s[32])
```

which is good, but the actual primitive API remains:

```c
void x25519_shared_secret(uint8_t out[32],
                          const uint8_t priv[32],
                          const uint8_t peer_pub[32])
{
    x25519(out, priv, peer_pub);
}
```

There is no rejection there.

That means a caller can accidentally do:

```text
X25519(...)
    ↓
all-zero result
    ↓
HKDF
    ↓
TLS keys
```

RFC 7748 recommends rejecting an all-zero result from X25519 key agreement.

### Fix

Make the API itself fail:

```c
int x25519_shared_secret(...);
```

and have it perform a constant-time zero test before returning success.

Do not rely on every caller remembering to invoke `shared_is_zero()`.

**Severity: High**

---

## 2. High: your pinning is bypassable through hostname canonicalization

This is the most interesting new hole I found.

Your pin lookup uses:

```c
ticket_host_eq()
```

which is byte-for-byte case-sensitive.

But DNS hostnames are case-insensitive, and your actual certificate hostname matching is already case-insensitive.

So:

```text
github.com
GITHUB.COM
Github.Com
```

can be treated as different pin-cache keys.

More importantly, your preload pin:

```text
github.com
```

does not apply to:

```text
GITHUB.COM
```

because the preload lookup is also case-sensitive.

The trailing-dot case has the same problem:

```text
github.com
github.com.
```

Your certificate matcher explicitly strips the trailing dot, so those names ultimately identify the same DNS host, while the pin layer treats them separately.

That means the security properties of:

> "this hostname is pinned"

aren't actually equivalent to the security properties of your certificate verifier.

### Fix

Canonicalize the hostname once, before:

* SNI
* certificate matching
* pin lookup
* pin storage
* ticket lookup/storage

At minimum:

```text
ASCII lowercase
+
remove one terminal dot
+
validate hostname syntax
```

Then use that canonical representation everywhere.

Do not simply make `ticket_host_eq()` case-insensitive while leaving separate representations elsewhere. One canonicalization function is much safer.

**Severity: High for the pinning threat model, otherwise Medium**

---

## 3. Medium: HTTP header detection is substring-based rather than line-based

`tls_response_complete()` scans every byte position looking for:

```text
content-length:
transfer-encoding:
```

It doesn't establish that the match starts at an HTTP header-field boundary.

That creates parser differentials.

For example, something embedded inside another header value can potentially be interpreted as a real header by this routine.

The same issue exists for the `chunked` token detection. You're doing essentially substring recognition rather than parsing the field-value according to HTTP grammar.

This is primarily a **response parsing / truncation / availability** issue rather than a direct TLS confidentiality break, but this code sits directly on the boundary between an untrusted server and application data.

### Fix

Parse:

```text
header-line := field-name ":" OWS field-value
```

one line at a time.

Only recognize `Content-Length` or `Transfer-Encoding` when the field-name itself matches exactly.

Also reject conflicting duplicate `Content-Length` values rather than selecting whichever occurrence your scan encounters.

**Severity: Medium**

---

## 4. Medium: duplicate HTTP framing headers deserve explicit rejection

Related to the above, I don't see a strong rule equivalent to:

```text
multiple Content-Length headers:
    accept only if byte-for-byte identical
    otherwise reject
```

and similarly:

```text
Transfer-Encoding + Content-Length
```

should have a deliberately defined policy.

You don't want your "is this response complete?" logic and eventual HTTP consumer to disagree about message boundaries.

This is a classic request/response smuggling class of bug.

**Severity: Medium**

## 6. RNG is still the weakest architectural component

The new RNG is more defensible, but I still don't like the fundamental model.

Your documented fallback entropy model is:

```text
RDTSC / RTC
timer timing
input/IRQ timing
```

when hardware RNG isn't available.

You correctly fail closed rather than claiming those are cryptographically strong.

That's good.

But the code still exposes:

```c
rand_seed()
rand_stir_src()
```

and the caller supplies the source classification.

So the security property partly relies on trusted callers correctly saying:

```c
RAND_SRC_RDSEED
RAND_SRC_INPUT
...
```

The entropy classifier itself doesn't authenticate the provenance.

For a kernel-internal API that's acceptable if the API is strictly internal. I would make that explicit by reducing the public surface or splitting trusted/internal functions from external ones.

## 7. One RNG ordering issue remains worth fixing

`rand_hw_init()` does:

```c
got |= hw_bytes(RAND_SRC_RDSEED, rdseed32);
```

and `hw_bytes()` calls:

```c
rand_stir_src(hw, cls);
```

Only **afterward** does it do:

```c
hw_present = 1;
```

So the reseed triggered by that hardware sample evaluates readiness before `hw_present` has been set.

You don't appear to get a direct security failure from this because the lifetime/freshness gates prevent premature readiness in the normal boot sequence, but it's unnecessarily subtle.

Set the hardware-presence state before the sample can trigger a reseed, or pass the tier information directly into the reseed decision.

---

## 8. Host build is currently broken

I compiled the C sources with aggressive warnings and found:

```text
tls_client.c:1477:
implicit declaration of function 'secure_zero'
```

because `rand.h` is only included under:

```c
#ifdef KERNEL
#include "rand.h"
#endif
```

while `tls_state_wipe()` calls `secure_zero()` unconditionally.

So the non-kernel build currently has an unresolved declaration.

That's not a cryptographic vulnerability, but it is exactly the sort of build/configuration divergence I don't want in security-sensitive code.

**Fix:** put the secure-zero declaration in a common header, or provide a common implementation independent of `KERNEL`.

---

## 9. `-Wconversion` is showing places I'd tighten

There are a lot of warnings around:

```c
uint32_t -> uint16_t
size_t   -> uint32_t
uint32_t -> uint8_t
```

particularly in TLS extension construction.

Most are probably safe because the values are structurally bounded, but for this project I would eliminate them rather than suppress them.

For example:

```c
put_u16(buf + start + 2, body_len);
```

should ideally be preceded by an explicit assertion/check proving:

```text
body_len <= UINT16_MAX
```

That turns a compiler warning into an executable invariant.
