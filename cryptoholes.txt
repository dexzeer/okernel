I reviewed the uploaded stack as a security/code audit, including the TLS 1.3 client, X25519, AEAD, RSA/ECDSA, X.509, OCSP, HKDF, and RNG layers.

There are some good defenses already present, but I found several holes worth fixing.

### Highest priority

1. **Truncated TLS response can be reported as a clean success**

   `tls_client.c:1129-1135` treats any `recv()` failure/EOF as normal completion:

   > `if (r < 0) ... TLS_PH_DONE`

   That is dangerous because `tls_recv_record_st()` can return `-1` with a **partially received TLS record** in `rec_buf`. More importantly, the client accepts EOF after application data without requiring an authenticated `close_notify`.

   An on-path attacker who can terminate the TCP connection can therefore potentially turn:

   `complete response` → `truncated response`

   while the API returns `TLS_STEP_DONE`.

   This is a **response-integrity/truncation vulnerability**, particularly serious because the API exposes only `out/out_len`, so callers can easily interpret the result as complete.

   **Fix:** distinguish:

   * EOF before any response bytes: policy-dependent
   * EOF with `rec_have != 0`: fatal truncation
   * EOF without authenticated `close_notify`: normally fatal unless the HTTP layer has independently established message completeness, e.g. validated `Content-Length`.

2. **`tls_state_wipe()` does not compile from the supplied sources**

   `tls_client.c:1246+` calls `secure_zero()`, but there is no definition or declaration anywhere in the supplied `.c/.h` files.

   My direct compile produced:

   `error: implicit declaration of function ‘secure_zero’`

   The supplied `tls_client.o` is also stale relative to the source: it does not reference `secure_zero` at all.

   This means the archive contains **source/object divergence**, which is a real supply-chain/build-integrity problem for crypto code. You can end up reviewing one implementation while the build consumes another.

   **Fix:** clean-build everything from source, delete checked-in `.o` files, and make CI fail on stale/generated object mismatches.

3. **AEAD has a global static scratch buffer**

   `aead.c:31`:

   ```c
   static uint8_t scratch[AEAD_MAC_SCRATCH];
   ```

   The code explicitly relies on a single-threaded contract. That's fragile for a crypto primitive. Any future interrupt, callback, nested invocation, parallel connection, or accidental reentrancy corrupts the MAC computation.

   This is currently mitigated by the stated architecture, so I'd call it **medium severity**, but it is exactly the kind of assumption that eventually gets violated.

   **Fix:** make Poly1305 streaming, or put the scratch/context in caller-owned state.

### Certificate validation concerns

4. **The certificate-chain builder is order-dependent**

   `cert_verify()` only walks the certificates in the order supplied by the server:

   `leaf -> cert[1] -> cert[2] -> ... -> trusted SPKI`

   It does not perform path building or try alternate issuers.

   That's mainly an interoperability/availability problem rather than a direct authentication bypass, but it means valid chains can fail depending on server ordering or cross-signing structure.

5. **Trust is actually SPKI pinning, not conventional CA validation**

   `spki_in_roots()` accepts a certificate whenever its SPKI hash matches an embedded root hash.

   That's a legitimate trust model, but it means the embedded "roots" are really **public-key pins**. In particular, when the leaf SPKI itself matches an embedded root, `cert_verify()` returns success without requiring that leaf to chain to anything.

   If intentional, document this prominently. If the intended model is conventional Web PKI, this is a semantic hole.

6. **RSA modulus validation is incomplete**

   `rsa_pub_from_x509()` checks:

   * odd modulus
   * at least 2048 bits
   * exponent is odd and >= 3
   * exponent fits one 32-bit limb

   But it doesn't enforce the normal RSA public-key constraint `e < n`.

   This is unlikely to produce a practical authentication bypass because the key is attacker-controlled and verification remains mathematically constrained, but it should be tightened.

### TLS protocol limitations

7. **ServerHello fragmentation is rejected**

   The state machine requires the entire ServerHello to be in the first record:

   `tls_client.c:639-652`

   TLS permits handshake messages to be fragmented across records. This is an interoperability/DoS issue, not normally an authentication break.

   The later handshake reassembly code correctly handles fragmentation, so this looks like an inconsistent implementation boundary.

8. **No TLS KeyUpdate support**

   Post-handshake code explicitly rejects anything other than NewSessionTicket.

   That's acceptable for a deliberately minimal client if documented, but a compliant TLS 1.3 peer can send KeyUpdate. Again, mostly availability/interoperability rather than a cryptographic hole.

### RNG

The RNG is better than I'd expect for a freestanding implementation. It has:

* hardware RNG integration
* entropy source classes
* reseeding
* forward rekeying
* readiness gating
* no deterministic fallback

But one thing bothers me:

`rng_rekey()` does:

```c
chacha20_encrypt(rng_key, rng_nonce, rng_counter, block, block, 64);
```

where `block` is uninitialized input. ChaCha20 encryption mathematically makes this equivalent to generating keystream, so the output is fine, but it triggers compiler diagnostics and is needlessly obscure.

I'd replace it with an explicit ChaCha20 block/keystream API or zero the input buffer first.

More importantly, **the RNG needs dedicated statistical/cryptographic state-transition tests**, especially around:

* snapshot/restore
* first-seed readiness
* repeated reseeding
* source failure
* RDRAND/RDSEED failure
* counter exhaustion

### Crypto primitives

I tested the supplied implementations against standard vectors for:

* SHA-256
* ChaCha20
* Poly1305
* X25519

Those basic vectors passed. In particular, the X25519 implementation produced the RFC 7748 known result, so I do **not** see an obvious primitive-level break there.

The AEAD construction also follows RFC 8439 correctly and uses a constant-time 16-byte tag comparison.

### My priority order

| Priority     | Finding                                                             | Impact                           |
| ------------ | ------------------------------------------------------------------- | -------------------------------- |
| Critical-ish | EOF/truncation treated as successful TLS completion                 | Response integrity               |
| High         | Source/object mismatch + broken clean build                         | Build integrity                  |
| Medium       | Global AEAD scratch buffer                                          | Reentrancy/concurrency           |
| Medium       | Trust model is SPKI pinning rather than ordinary CA path validation | Authentication semantics         |
| Medium       | No ServerHello fragmentation                                        | Interoperability/DoS             |
| Low/Medium   | RSA `e < n` not enforced                                            | Key validation                   |
| Low/Medium   | No TLS KeyUpdate                                                    | Interoperability                 |
| Low          | Uninitialized buffer passed as ChaCha plaintext                     | Code quality/compiler robustness |

The **EOF/truncation issue is the one I'd fix first**. It crosses the boundary from "minimal TLS implementation limitation" into "application can accept attacker-truncated authenticated data as a successful response."
