# AGENTS.md — KAnarchy OS (okernel kernel)

## What this is

From-scratch OS in C + x86 assembly. The kernel is okernel, the desktop is **Okapi**, the browser is **okai** (see HANDOFF.md for the orientation). Two build targets: text mode (VGA text) and desktop mode (1920x1080 GRUB framebuffer). Runs in QEMU. No standard library, no Linux, no BIOS calls in protected mode.

## Build

```bash
make desktop       # Desktop ISO (kanarchy-desktop.iso) — primary target
make text          # Text mode ISO (kanarchy-text.iso)
make clean         # Nukes all .o, .bin, .iso, isodir/
```

Requires: `gcc` (multilib), `nasm`, `ld`, `grub-mkrescue`, `xorriso`, `mtools`.

Desktop QEMU command (must use `-vga std` for framebuffer; `-device e1000` for networking — okai/HTTPS need it):
```bash
qemu-system-i386 -accel kvm -accel tcg -m 512 -cdrom kanarchy-desktop.iso -boot d -vga std -device e1000,netdev=net0 -netdev user,id=net0
```
**Use hardware acceleration.** Pure emulation (TCG) runs the kernel ~10x slower (a Wikipedia relayout: ~300ms TCG vs ~30ms KVM). Linux: `-accel kvm` (needs `/dev/kvm` access). Windows: `run-windows.bat` — `qemu-system-x86_64 -accel whpx -accel tcg` (the Windows **i386** build has no WHPX; the 32-bit kernel boots fine in x86_64 QEMU; verified 2026-10-07: boot to heap 2s, mouse wheel mode OK).

Serial debug variant (for TLS/network bring-up — serial is ground truth for network bugs):
```bash
qemu-system-i386 -m 512 -cdrom kanarchy-desktop.iso -boot d -vga std -device e1000,netdev=net0 -netdev user,id=net0 -nographic -serial stdio
```

## Gotchas that will bite you

- **BIOS interrupts don't work.** We're in protected mode after GRUB. No `int 0x10`, no `int 0x13`. All hardware access is via port I/O (`inb`/`outb`).
- **Framebuffer is above 4MB** (typically `0xFD000000`). Must set up identity-mapped page tables in `paging.c` before accessing it. Without paging, writing to the framebuffer = instant triple fault.
- **The cursor is NOT in the backbuffer (2026-10-08, `src/cursor.c`).** It is alpha-blended straight onto the framebuffer, moved inside the mouse IRQ (restore old rect from the backbuffer, blend the new one), and `graphics_flush()` copies dirty rows in short interrupt-free chunks then re-blends it (`cursor_fb_repair`). Never draw a cursor into the backbuffer or recomposite the scene because the mouse moved — the old per-iteration erase/recomposite was the main source of lag and of hover artifacts. Packets apply 1:1 (9-bit sign + overflow, no smoothing), 200 Hz sample rate. PS/2 init (`mouse_init_fb`) disables both ports, flushes, and reads EVERY controller reply with a wait, in order — the old code read the config byte without waiting, so a key held during boot was written back as the config and cleared the translate bit: 'a' typed Enter, every release retyped the key (`test_boot_keys.py`).
- **Never a bare `sti` in code reachable from an IRQ (2026-10-08).** Handlers run after EOI with IF=0; re-enabling interrupts inside one lets the next IRQ of the same line nest — `rand_stir_src` (called from the keyboard IRQ) did `cli`/`sti` and keystrokes came out LIFO ("abcdef" → "fedcba"). Save/restore EFLAGS.IF (`rng_cli`/`rng_sti`, `irq_save` in cursor.c). `test_typing.py` guards it.
- **The main loop halts when idle (2026-10-08).** No composite, no mouse motion/buttons/wheel, no drag, no fetch in flight and no okai work (`okai_wants_cpu`: loading, render pending, animating, JS due) → `hlt` until the next IRQ. Busy-spinning hammered e1000 MMIO so hard that QEMU's timer starved and PIT ticks were lost (kernel clock ~30% slow). `[fps] N loops=M busy=P%` is the 1 Hz perf line (`bench_mouse.py`). The halt is `cli; check key queue; sti; hlt` so a key queued just before it never waits a whole tick.
- **Keystrokes are queued, never handled in the IRQ (2026-10-08).** The keyboard IRQ only pushes (char, Alt-at-press) into `key_q` in `desktop.c`; `keys_dispatch()` at the top of the main loop runs `on_keypress`. Shell commands, okai navigation (frees the document), page JS (the ojs realm is not reentrant) and scrolls must never run on top of the main loop from IRQ1. Modifier state for chords (Ctrl+Alt+T) travels with the key — reading `keyboard_alt_held()` at dispatch time misses chords released before the loop gets there.
- **No backbuffer flicker fix is intentional.** We use a backbuffer with dirty-row tracking. `graphics_flush()` copies only changed rows to the framebuffer. If you remove the backbuffer and write directly, you get flicker. If you remove dirty-row tracking, FPS drops from 160+ to ~5.
- **Mouse: IntelliMouse 4-byte wheel mode IS supported** (negotiated in `mouse_init_fb`, `src/cursor.c`). It sends the 200/100/80 sample-rate magic + `0xF2` (get ID), then must wait for the ACK and the ID byte **in order** — draining the output buffer then reading a not-yet-arrived byte desyncs the PS/2 stream and kills movement shortly into the session (HANDOFF bug #25). On `id == 0x03/0x04` it sets `mouse_has_wheel` and the 4th byte is read as the wheel delta. Don't break that handshake ordering.
- **High-half kernel (2026-09-07).** Desktop links at 0xC0100000 (`linker-high.ld`; text keeps `linker.ld`). LOW trampoline `_start` (e_entry=0x100030, ESP 0x7FF00) + private boot GDT (GRUB's 0x08 is invalid) → `_start_high` → `kernel_main`. The boot PD maps phys 0-64M with 4MB PSE pages (identity + high): the image + .bss (boot stack included) is ~11MB now — a 4M boot map triple-faults silently before serial init. Order: memory → mboot copy (fb@88/pitch@96) → `paging_init` (uncond) → process → graphics (identity FB, never `paging_map` window). `V2P`/`P2V_U32` in `src/memlayout.h`. Traps: LOW e_entry, boot GDT, paging-before-process, identity FB, explicit 2nd user page + full 4K copy. See HANDOFF Priority 2.
- **SMP (2026-10-09; `src/acpi.c`, `lapic.c`, `smp.c`, `boot/ap_tramp.asm`, `boot/smp_stubs.asm`).** `acpi_init` (right after `paging_init`) finds the RSDP (EBDA, BIOS area, then the multiboot memory map's ACPI regions for UEFI) and parses the MADT (CPUs, I/O APICs, overrides); `smp_init` (before `sti`, after the PIT is programmed) enables the boot CPU's LAPIC (virtual wire kept: LINT0 = ExtINT, the 8259 stays the device interrupt controller; x2APIC if firmware left it on, or for APIC ids > 254) and wakes every other CPU with INIT + SIPI through a real-mode trampoline copied to phys 0x8000 (patched cr3/stack/entry slots; APs run on the kernel page directory and the shared GDT/IDT, no TSS). **APs only run jobs**: `smp_parallel_for(fn, ctx, n, grain)` (`fn(ctx, item, cpu)`) — they never touch the scheduler, process table, windows, serial or okai, so none of that needs to be reentrant. Jobs may use kmalloc/kfree (the heap and the page allocator are spinlocked with IRQs off) and x87; nested calls run inline; an exception on an AP only parks that CPU (`smp_fault_hook`, weak in `idt.c`). Wake-up is a fixed IPI (vector 0xF0) to `hlt`ing APs; job slots are recycled with a gen/active handshake (see `smp.c`), so the caller never waits for sleeping APs. Local APIC/IOAPIC MMIO is the identity-mapped uncached window 0xFEC00000-0xFEFFFFFF created in `paging_init` (before any process, so every page directory copies it). Tests: `smp` / `smp test` in the shell, `tests/headless/test_smp.py` (-smp 1/2/4/8), `tests/test_acpi.c` (parser fuzz under ASan), `tests/headless/smp_win.ps1` (WHPX, x2APIC via `make kanarchy-x2apic.iso`; TCG cannot do x2APIC). QEMU test hooks: `OKVM_SMP=n`, `OKVM_CPU=model`.
- **Damage tracking + the flush (2026-10-09, `src/graphics.c`).** Every drawing primitive records the dirty span `[dx0,dx1)` of each row it touches (`mark_span`) and the row range `[dirty_ylo, dirty_yhi)`; `graphics_flush` returns at once when nothing is dirty and otherwise copies only the union span of each run of rows (was: whole 1920px rows, and a scan of all 1080 flags on every main-loop spin, which was 2/3 of ALL cycles while a page loaded - measured with the profiler). Code that writes `graphics_get_buffer()` directly must call `graphics_mark_dirty(y)`/`graphics_mark_rect`. Self check: shell `gfxcheck` flushes and compares the framebuffer with the backbuffer outside the cursor (`tests/headless/test_gfx_verify.py`; a mutant that drops the marks fails it). Profiler: shell `prof on` logs `[prof] zone=Mcycles/calls` once a second (`src/prof.h`; Windows driver `tests/headless/prof_win.ps1`: scroll / mouse / idle phases under WHPX).
- **Framebuffer is write-combining (2026-10-09, `pat_init` in `paging.c`).** The PAT's entry 1 (PWT) is programmed to WC on every CPU and the framebuffer windows are mapped with PWT. On real hardware the aperture is in the PCI hole, which firmware leaves uncached (MTRR UC); a write-back mapping then makes a 1080p frame take seconds, PAT=WC overrides the MTRR. A framebuffer above 4GB (UEFI Above-4G decoding) cannot be mapped by this 32-bit kernel (logged). Untested on real hardware.
- **SSE2 is enabled (2026-10-09), but only `src/simd.c` and `src/media/vp9_simd.c` may use XMM (`src/fpu.c`).** Everything else stays `-mno-sse`; `simd.o`/`simd_test.o`/`vp9_simd.o` are the only objects built `-msse2` (vp9_simd runs from thread context only: `vp9_simd_ok()` checks `fpu_has_sse2()`). `fpu_init_cpu()` (every CPU, APs too) sets CR0/CR4 (OSFXSR, OSXMMEXCPT) and context switches save/restore FXSAVE images (`fx_state` at the tail of `struct process`; FNSAVE fallback without FXSR). Interrupt handlers (cursor.c, timer, keyboard ...) must never touch XMM: they do not save it. `simd_copy`/`simd_copy_stream` (non-temporal, flush into the WC framebuffer)/`simd_fill32` fall back to plain loops without SSE2. Shell `simd`: reference-checked copy/fill, FXSAVE round trip, throughput (rep movs 26 vs SSE 15 Mcycles per 64MB under WHPX).
- **Display backends (2026-10-09; `src/display.h`, `vgpu.c`, `virtio.c`, `pcix.c`).** `graphics_flush` turns the dirty spans into rectangles and hands them to the active backend: the GRUB framebuffer (`fb_present`, software cursor on the framebuffer, the fallback that works everywhere), virtio-gpu (`vgpu_probe`, run from `graphics_init`) or `i915_probe` (Intel iGPU, later step). virtio-gpu uses the BACKBUFFER as the resource's backing store (one attach entry; the heap is physically contiguous), so a frame is TRANSFER_TO_HOST_2D of the damaged rects (pipelined, one doorbell) + one RESOURCE_FLUSH - no CPU pixel copy at all - and the pointer is the device's hardware cursor (cursorq, fire-and-forget moves from the mouse IRQ; `cursor_set_display` in cursor.c; the sprite is converted to straight-alpha ARGB). It needs virtio 1.x (VERSION_1), modern PCI caps, a BAR below 4GB, and runs polled (INTx masked, queues set NO_INTERRUPT). Device MMIO windows come from `paging_map_mmio` (uncached, 16 x 4MB pool, boot-time only: page directories copy the kernel half when created). QEMU: `-vga virtio` (virtio-vga also gives GRUB its VGA/VBE mode); tests: `OKVM_VGA=virtio python3 tests/headless/test_gfx_verify.py` hashes 16-row bands of the backbuffer in the kernel (`gfxsum`, taken after the next flush) and of QEMU's screendump. The hardware cursor is not part of a screendump (check `-trace enable=virtio_gpu_update_cursor`).
- **The screen size is the bootloader's (2026-10-09; `gfx_w/gfx_h`, `SCREEN_W/H` are variables).** `graphics_init` takes the multiboot framebuffer mode (32bpp only, 640x480 .. 4096x2304) and everything sizes itself from it; the multiboot header still ASKS for 1920x1080 (`VID_W/VID_H` in `start.asm`), GRUB falls back to the closest/`auto` mode when the adapter lacks it (QEMU's VGA gave 1280x800 for a 1366x768 request) and the kernel adapts. Static tables that were sized by the screen are now sized for 1920x1080 or the 4096x2304 max (`window.c` terminal cell grids). The wallpaper (authored 1920x1080) is bilinear cover-fit resampled (`graphics_scale_to_screen`); `paging_init` maps as many 4MB framebuffer windows as the mode needs. Tests: `make kanarchy-res.iso VID_W=.. VID_H=..`, `tests/headless/test_resolution.py` (1024x768, 1280x800, 1920x1080, 2560x1440; virtio too).
- **Intel integrated graphics: groundwork only (2026-10-09; `src/i915.c`, shell `gpu`).** `i915_probe` (from `graphics_init`) only READS PCI config (id, BARs + sizes) and maps BAR0 uncached, then returns NULL: the display keeps using the GRUB framebuffer. `gpu` prints a read-only report: generation (device-id table, host-tested), BARs, GMCH/stolen memory, where the GRUB framebuffer sits relative to the aperture, and per pipe A-C the PIPECONF/plane/cursor registers and the GTT entry behind the scanout surface. Nothing writes a register. Register offsets used (pipe A, +0x1000 per pipe): PLANE_CTL/DSPCNTR 0x70180, stride 0x70188, surface 0x7019C, PIPESRC 0x6001C, HTOTAL 0x60000, VTOTAL 0x6000C, cursor 0x70080/84/88; GTT = upper half of BAR0 (assumption from the PRMs, unverified on hardware). Test build `make kanarchy-i915test.iso` (probe pointed at QEMU's VGA, forced Gen9) runs the whole path in `tests/headless/test_i915_probe.py`. Untested on a real Intel GPU: the `gpu` output from the target machine is what the next step (scanout from our own buffer / hardware cursor) needs.
- **UEFI boot + the laptop image (2026-10-10; `src/fbtext.c`, `boot/laptop-grub.cfg`, `LAPTOP.md`, `make laptop`).** `kanarchy-laptop.iso` boots on legacy BIOS AND UEFI (grub-mkrescue puts `BOOTIA32.EFI` + `BOOTX64.EFI` in an ESP when `grub-efi-amd64-bin` + `grub-efi-ia32-bin` are installed; tested under OVMF 64- and 32-bit with `/usr/share/OVMF`, ISO attached as a USB disk). A UEFI machine has NO VGA text memory, so the text-mode hardware report also exists as `kanarchy-fbtext.bin` (text kernel built `-DFBTEXT`: the terminal draws its 80x25 cells into RAM, `fbtext_present` converts the changed cells to pixels on the GRUB framebuffer, 24/32 bpp, glyphs = the Terminus 16x32 font box-filtered to the cell size; falls back to 0xB8000). The GRUB config picks it as the default when `$grub_platform` is efi and loads `efi_gop` (NOT `all_video`: the bochs driver then wins in QEMU and reports a stride GOP does not have). **Memory under UEFI:** firmware leaves ACPI/reserved holes right above 1MB (OVMF: 7MB usable, then NVS), so `mem_upper` is useless; `memory_init` now frees only type-1 pages of the multiboot memory map above the kernel image (bit 6), and `heap_init` takes the LARGEST free run above the kernel. Also fixed: `MULTIBOOT_FLAG_MEM` was bit 1 (boot device, which GRUB-EFI does not set) instead of bit 0, so the kernel saw 15MB. Open risks on real firmware: the kernel image must fit in usable memory at 1MB (GRUB refuses otherwise), the mbi must sit below 64MB (the boot PD maps 0-64M; seen at 0x10000-0x26000), a framebuffer above 4GB is unusable, QEMU rounds a 1366-wide mode to 1360 (sheared picture in OVMF: emulator artefact, GOP reports the real stride on hardware).
- **Power-off, reset, and the first real `gpu` (2026-10-10; `src/acpi_pm.c/.h`, `acpi.c`, `hwinfo.c`).** `shutdown` used to poke only QEMU's ports, so a real laptop froze. `acpi_parse_fadt` (PM1a/PM1b control ports, SMI_CMD/ACPI_ENABLE, hardware-reduced SLEEP_CONTROL, RESET_REG) and `acpi_find_s5` (the `_S5_` package in the DSDT AML gives SLP_TYPa/b) are pure and host-tested (`tests/test_acpi.c`); `acpi_pm_poweroff` switches to ACPI mode if SCI_EN is clear, writes SLP_TYP then SLP_TYP|SLP_EN like Linux, waits 2 s, then tries the emulator ports. `acpi_pm_reboot`: ACPI reset register, keyboard controller 0xFE, PCI 0xCF9, triple fault. The desktop gets the facts from `acpi_init` (`acpi_get_pm`, serial line `[acpi] power: ...`), the text/report kernel from its own table walker (`build_pm` in hwinfo.c; `acpi` prints a `power:` line). Verified under QEMU only (PIIX4 B004 and q35 604, BIOS and OVMF): exit is immediate; real firmware untested. The first real `gpu` (Cherry Trail laptop, 8086:22b1, Pentium N3700 class) showed every pipe as 0: Valleyview/Cherryview put the display engine at BAR0 + 0x180000 (`i915_display_base`). New report command `input`: ACPI `_HID`/`_CID` scan of DSDT/SSDTs (is the touchpad PS/2 `PNP0F13` or I2C-HID `ELAN`/`SYNA`/`PNP0C50`?) and a timed PS/2 aux-port probe (reset replies, Synaptics identify, 10 s of packet capture; interrupts off, PIT-timed).
- **USB mouse: xHCI driver (2026-10-11; `src/xhci.c/.h`, `mouse_inject` in cursor.c, shell `usb`).** The target laptop (Cherry Trail, 8086:22b5 xHCI at 00:14.0) has an I2C-HID touchpad and NO PS/2 pointer (`input` showed port self-test ff / reset reply fe), so USB is the way to a pointer. `xhci_init` runs at boot after `mouse_init_fb` (register window from `paging_map_mmio`, so before the first process): PCI D0, BIOS->OS handoff (legacy-support capability), halt+reset, DCBAA (+scratchpads), command ring, one 64-TRB event ring (interrupter 0, polled: ERDP/EHB handshake), ports powered, then each connected port: reset (USB 2) or already enabled (USB 3), Enable Slot, Address Device, GET_DESCRIPTOR (8 bytes for the real EP0 size, Evaluate Context if it differs), config descriptor walk for a class 3/sub 1/proto 2 interface with an interrupt IN endpoint, SET_CONFIGURATION, SET_PROTOCOL(boot), Configure Endpoint, then 16 Normal TRBs (IOC|ISP, length = max packet) stay in flight; every completion is parsed (buttons, dx, dy, wheel) and re-queued. `xhci_poll` (main loop, 100 Hz at worst since nothing interrupts) handles port-change events: unplug frees the slot, plug re-enumerates. Non-mouse devices are addressed, identified in the log, and their slot disabled again. Hubs, USB keyboards and bulk/mass storage are not handled. All DMA structures are 4KB aligned heap memory (V2P); contexts are 32 or 64 bytes per HCCPARAMS1.CSZ. A BAR above 4GB cannot be mapped (OVMF puts qemu-xhci there: test with `-fw_cfg name=opt/ovmf/X-PciMmio64Mb,string=0`). Boot with `nousb` on the multiboot command line to skip it (laptop menu entry 2n). Tested under QEMU: BIOS and OVMF, enumeration of a USB 3 device, motion + both buttons, 3x plug/unplug (scripts were scratch files; the QEMU recipe: `-device qemu-xhci,id=xhci -device usb-mouse,bus=xhci.0`, `info mice` + `mouse_set N`, HMP `mouse_move`/`mouse_button`). Real hardware: untested. **Rewritten as a general pointer driver the same day (the first laptop run said "xHCI up, no mouse" with a plugged-in mouse, and the serial log is unreadable there):** the device is no longer required to be a boot-protocol mouse. `src/hid.c/.h` (pure, host-tested with fuzzing: `tests/test_hid.c`, in `make host-tests`) parses the HID REPORT DESCRIPTOR of every class-3 interface (GET_DESCRIPTOR 0x22) and returns the layouts of the input reports that belong to a Generic Desktop Mouse/Pointer application collection (X, Y, wheel, AC Pan, buttons 1-8, report ids, 8-32 bit fields, signed/unsigned, relative or absolute); `hid_decode` turns a report into dx/dy/wheel/buttons (absolute axes scaled to 0..65535, then to the screen in `ptr_report`). The boot-protocol layout is only the fallback (interface 1/2 whose descriptor cannot be read or has no pointer; SET_PROTOCOL(boot) only then). Up to 6 pointer endpoints at once (composite wireless receivers, a mouse plus a tablet), all started in ONE Configure Endpoint. Hubs: USB 2 hubs (high speed with the TT fields in the slot context, FS/LS, nested up to 5 deep, route strings) get the slot context Hub/MTT/ports update, their ports powered and POLLED with GET_PORT_STATUS from `xhci_poll` every 200 ms (no hub interrupt endpoint); SuperSpeed hubs are refused (log line). Ports are polled state, not events: every 200 ms each root/hub port with a device and no `known` flag is enumerated (4 tries, 300 ms apart, reset again each time; `usb rescan` clears the counters); a vanished or replaced device drops its slot and everything behind it. Error recovery: control-endpoint STALL/timeout -> Reset Endpoint (+Stop Endpoint) + Set TR Dequeue, descriptor reads retry 3x; a halted pointer endpoint is reset and refilled by `xhci_poll` (5 tries, counter cleared by the next good report); completion codes 26/27 (Stopped) are our own Stop Endpoint leftovers and are ignored. Because the laptop has no serial port everything also goes to an on-screen log: `xlog` keeps the last 40 lines (and writes serial); `usb` prints the controller, every connected root port with its PORTSC, every pointer endpoint (reports/errors/unmatched) and the last 14 log lines (device ids, each interface's class/subclass/protocol, the parsed layout, the first two raw reports of each pointer); `usb rescan`; `usb selftest` provokes a STALL on every device and stops/restarts every pointer endpoint. All control transfers are bounded to 1 s. The cursor only moves when the main loop polls (100 Hz when idle). Tested under QEMU (xHCI): usb-mouse (boot), usb-tablet (class 3/0/0, ABSOLUTE: the first driver could not have started it), a mouse behind a hub and behind two nested hubs, hot-plug on a root port and behind a hub then unplug, keyboard + mouse + tablet together (keyboard identified and left alone), selftest (STALL code 6 recovered, endpoint restarted, the mouse keeps working), UEFI with a SuperSpeed boot stick + hub + mouse + tablet; absolute input via QMP `input-send-event`. Not testable here: real devices' quirks, SuperSpeed hubs, report ids with 16 bit axes on the wire (only in the host test).
- **Touchpad: I2C-HID driver that finds its own controller (2026-10-11; `src/i2chid.c` glue, `src/dwi2c.c` DesignWare master, `src/hidi2c.c` protocol, `src/i2caml.c` AML finder, `src/ptp.c` gestures, `src/hid.c` touch parser, `src/devlog.c`; shell `touchpad`, `touchpad aml`, `touchpad retry`; report-kernel `i2c`/`i2c scan` remain).** The laptop's touchpad is SYNA3602 at I2C 0x2C on `\_SB.PCI0.I2C5` (LPSS DesignWare I2C, ACPI id 808622C1, no PCI function, base 0 in the AML template). `i2chid_init` (boot, after xhci_init, before the first process; `noi2c` on the command line skips it) copies the DSDT/SSDTs (`acpi_aml_tables`), `i2caml_find` pattern-scans them for a Device with a known touchpad `_HID`/`_CID` (SYNA/ELAN/ALPS/CYAP/MSFT0001/PNP0C50/ACPI0C50...) holding an I2cSerialBusV2 resource (address, speed, controller path) and collects the `_DSM` Return constants as HID-descriptor-register candidates (+ 0x20, 0x01, 0, 2, 0x10, 0x30, 0x100). ONLY when such a device exists it scans the PCI hole 0x40000000-0xFEC00000 (skipping RAM/ACPI regions from the multiboot map, every PCI memory BAR, 0xE0000000-0xF0000000) one dword per 4 KB page through `paging_probe_window` (the 16th MMIO slot, a PSE 4MB uncached window re-pointed per block; boot only) for COMP_TYPE 0x44570140 at +0xFC (~700k reads, ~1 Gcycle under QEMU TCG), and tries the touchpad on every block it finds AS SOON AS it is found: DesignWare setup (standard mode, counts for a 100 MHz clock: SS 0x1F4/0x1F4, FS 0x55/0x99), HID descriptor read at each candidate register (valid = length 30, version 0x0100), a second pass after the LPSS kick (+0x804 |= 3 release resets, +0x800 |= 1 clock; unverified layout), then power on, RESET, report descriptor, `hid_parse_pointer` (mouse collection, what the device sends by default) and `hid_parse_touch` (Windows Precision Touchpad: Touch Pad application, Finger collections, tip/id/x/y, contact count, button; the Input Mode feature 0x0D:0x52 is set to 3 with a SET_REPORT so the device sends touch reports), then a try at fast mode (400 kHz) kept only if the descriptor still reads. Polling: `i2chid_poll` reads the input register (`max_in` bytes, plain read) once per 10 ms tick (no GPIO interrupt: unknown pin); length 0 / NACK = nothing; 20 consecutive timeouts stop it. `ptp.c`: one finger moves (pixels = units * screen_w / pad width, mild acceleration, sub-pixel remainders), two fingers scroll (yrange/30 per step, fingers up = page down), quick tap = left click, two-finger tap = right click (press now, release on the next poll), clickpad button = left button, hybrid reports (contact count > fingers in the report) are assembled. Everything is on screen via `devlog` (tag 't'; `touchpad`), and when the hunt fails the AML of the controller scope (`_CRS`/`_PS0`/`_STA` bytes) and memory/PCI-config OperationRegions go to tag 'a' (`touchpad aml`) - the data needed to find the real base. Tested: host (`tests/test_touch.c`, in `make host-tests`: the PTP descriptor parse/decode, every gesture, the DesignWare driver against a software model of the controller incl. FIFO limits/NACK recovery/TAR rules, HID-over-I2C against a model device incl. SET_REPORT bytes, the AML finder, ASan+UBSan fuzz of all of it), QEMU (an SSDT injected with `-acpitable sig=SSDT,file=...` makes the whole boot path run: AML found, scan over 715k pages without a hang, a fake DesignWare signature in an ivshmem BAR found with the test option `i2cbars` and failing gracefully, BIOS and OVMF; `usbt.py`/`mkssdt.py`/`i2ctest.sh` were scratch scripts). - **Scheduler is preemptive via `process_switch_to` (2026-09-08+).** `sched_tick()` (timer IRQ) switches kernel threads through the `context_switch` stub (isr.asm) with guards: never from ring-3 trap stacks (defers), never into un-entered/BLOCKED/ZOMBIE slots, `switch_busy` closes the drain window, per-slot `generation` aborts reuse-under-cli. `sched_yield()` on the INT 0x80 trap stack still NEVER switches CR3/ESP0 (slice reset only — the stub will popa+iret to ring 3). `process_switch` (lightweight CR3+ESP0) is handoff-point-only (entry/exit drains).
- **PCB offsets: offsetof only, fields go last (2026-09-10).** `idt.c`'s exec-redirect reads `user_eip/esp` via `offsetof(struct process,...)` — a past hardcoded `pcb[7]/pcb[8]` silently crossed EIP/ESP the moment a field was inserted mid-struct (exec resumed at EIP=user_esp, ESP=entered_ring3). New `struct process` fields go at the TAIL (see `generation`); never index PCB words by hand.
- **Syscall ABI (2026-09-08).** INT 0x80: 0=print, 1=exit, 2=write(fd 1→focused terminal), 3=getpid, 4=yield, 5=mmap_user. All user pointers go through `paging_user_range_valid()` (present+U/S at both levels) BEFORE dereference — a bad ring-3 pointer prints an error, never faults the kernel. `enter_user_mode` uses register convention (eip→EAX, esp→EDX, no stack args); sys_exit resumes via `user_exit_trampoline` (full caller-frame restore).
- **Yield is trap-safe (2026-09-08).** `sched_yield()` runs on the INT 0x80 trap stack (stub will popa+iret back to ring 3) — it must NEVER switch CR3/ESP0 there (the resume faulted as #PF at the next ring-3 EIP). It only resets the slice; handoffs happen at entry/exit safe points. Same class of bug as the timer-switch ban.
- **TCP discipline (2026-09-08).** Fast retransmit counts ONLY pure-ACK repeats (plen==0 threaded through `tcp_process_ack`) — data-carrying segments with a repeated ack field are NOT dup ACKs (counting them fired bogus fast-rtx mid-download and stalled the next connection). Reorder buffer (8×1500B) is per-connection (reset in `tcp_connect`); advertised window is 32KB (the old 60B stub throttled servers).
- **PFS traps (2026-09-08).** `fs_delete` copies the name before clearing (hook needs it); `pfs_sync_file` frees the old run before first-fit alloc; hydrate/sync buffers are static (32KB blows the 4KB trap stack). Editor Ctrl+S/Ctrl+X need the keyboard Ctrl tracker (0x1D) — the status bar advertised them unwired.
- **OkVM disk slot (2026-09-08).** `OkVM(tag, disk=path)` appends `-hda` for PFS tests; default runs stay diskless. A stale `-hda` QEMU holds the image write-lock (`qemu-img` fails) and its monitor socket refuses connects — kill it first.
- **`section .note.GNU-stack`** in .asm files MUST be the last section. If placed at the top, all subsequent code gets swallowed into the non-executable section and the kernel crashes on boot.
- **Compiler flags matter:** `-fno-pic -fno-pie -mno-red-zone` are required. Without them, GCC generates position-independent code with `__x86.get_pc_thunk` calls that crash in a freestanding kernel.
- **Image size** (~4.0MB text incl. 1.5MB embedded fonts, ~2.8MB BSS; `_kernel_end` ≈ 7.5MB phys). Must stay inside the boot PD's 64M window. Put big tables on the heap (segregated-fit `kmalloc`/`kfree`, RAM-sized: 414MB at `-m 512`), not in BSS.

- **TLS trust (2026-10-07).** Chains anchor two ways: a cert ISSUED BY a store root (name-bound: issuer DN == root subject, AKI == root SKI when both exist, signature verifies under the root key — `root_issued()` in `certverify.c`; servers don't send roots), or an in-flight cert whose SPKI is a root key. Certs past the anchor are ignored (expired cross-signs must not fail the path). Root store = Mozilla's, generated from NSS `certdata.txt` itself with `python3 tools/gen_roots.py certdata.txt` (download URL in the script): only roots trusted for server auth, plus Mozilla's distrust-after dates — a chain anchored at such a root is refused when the leaf's notBefore is later (`root_distrusts`). Never regenerate from the Debian PEM bundle: it dropped both, and we were still trusting four roots Mozilla had removed (Entrust, Chunghwa, SecureSign RootCA12, Atos 2011). OCSP staples: only a verified REVOKED status or a Must-Staple leaf hard-fails; stale/unverifiable staples soft-fail like an absent one. The staple's issuer is the flight's 2nd cert ONLY after it is proven to have signed the leaf (a root-anchored or pinned leaf leaves entry 1 unverified). X.509 parsing rejects duplicate extensions and trailing bytes inside extension values (differential-parsing class); NameConstraints honour the leading-dot form (".example.com" = subdomains only). Audit regressions: `test_adversarial.c` section 6 + `MOCK_ENC_CCS`/`MOCK_LATE_CCS`/`MOCK_MS_FORGED_ISSUER` (fixtures: `tests/adversarial/mint_audit.py`). Suites: ChaCha20-Poly1305 (preferred) + AES-128-GCM (`aes.c`, constant-time; Akamai sites need it); no SHA-384 suites, no TLS 1.2.
- **Makefile tracks headers via `-MMD -MP` (2026-10-07).** Never drop it: before it, `src/crypto/*.h` weren't dependencies, a grown `struct tls_state` left `tls_net.o` at the old size, and `tls_state_init`'s memset zeroed the neighbouring fetch-timeout clock — every HTTPS fetch "timed out" instantly and silently downgraded to HTTP. When in doubt, `make clean`.
- **Networking is parallel (2026-10-07).** `network.c` has a TCP socket table (`tcp_open/send/recv/close/abort`, 16 sockets, per-socket retransmit flight + reorder buffer + 256KB receive ring; the advertised window IS the ring's free space — never ACK bytes you can't keep) and a 32-entry DNS cache with concurrent queries (`dns_lookup`: 1/0/-1; ids reused across resends; late answers still update the cache). `src/net/fetch.c` runs up to `FETCH_MAX` (8) GETs at once over a keep-alive pool (`CONN_MAX` 8, 6 per host; idle connections reused, a stale reused connection that dies before the first byte retries fresh). okai keeps a request table (`struct oreq`): main document + up to `OKAI_SUB_PAR` (6) resources per tab, one engine slot always left for navigations. A finished request is DETACHED from the table before its response is processed — delivery can run scripts that navigate, and navigation cancels the tab's requests. The e1000 is polled (IRQs masked), 256 RX descriptors on the heap. Per-packet logs are behind `net_trace` (shell `nettrace`) — serial bytes are port-I/O exits.
- **Browser chrome is `okai_ui.c` (2026-10-07).** `ui_layout()` is the only place chrome geometry is computed — draw and hit tests both use it; don't reintroduce mirrored constants. It draws with the engine's rasterizer/font on the MAIN stack (fine: no deep recursion) into a cached band re-rendered only on a state-signature change — keep anything that changes per frame (spinner phase, hover) in `state_sig()` or it will not repaint. Title-bar-less windows' caption buttons are `window_ctrl_rect()` (window.c owns min/max/close clicks). The FPS counter lives in the taskbar.
- **Taskbar + title bars are AA too (2026-10-07).** `taskbar.c` renders a cached 1920x`TASKBAR_H` strip (frosted wallpaper, window buttons, FPS chip, RTC clock in UTC — no launcher: everything starts from the terminal) only when its signature changes, and only from the unclipped main-loop `taskbar_update()` (clipped damage repairs just blit the cache — re-rendering inside a repair rect left half-lit hover states); `tb_layout()` is the single geometry source for drawing and `taskbar_hit()`, logged as `[taskbar] btn win=N x,y,w,h` (okvm `vm.taskbar_rect(win)`). Title-bar windows get a GNOME-style dark header bar drawn straight into the backbuffer via `ui_draw.h` (`ui_screen_surf`, implemented in `okai_ui.c`); `title_btn_rect()` is the one source for their close/minimize hit boxes.
- **Wallpaper is a JPEG (2026-10-07).** `tools/wallpaper/kanarchy_wallpaper.html` (WebGL raymarcher) → `tools/wallpaper/render.sh` (headless Edge/Chrome + Pillow) → `wallpaper.jpg`, `incbin`-ed by `src/wallpaper.asm` and decoded at boot by the web engine's JPEG decoder into the heap (`graphics_set_wallpaper`).
- **memcpy/memset/memmove are `rep movs/stos` (2026-10-07).** The byte loops were the hottest code on the desktop (a page scroll memmoves ~7MB). They are inline asm so GCC cannot turn them back into self-calls; memmove's backward path sets DF and always clears it. Fuzzed against byte references on the host (-O0/-O2).
- **ISR/IRQ stubs `cld` before calling C (2026-10-08).** An interrupt can land inside memmove's `std` region; without the `cld` every handler's string ops (the timer's `rand_stir` memcpy, each tick) ran backwards over memory — a scroll-up on a big page corrupted the kernel and hung it with DF=1/IF=0. `irq_handler` logs `[isr] DF set` if DF is ever seen set (`test_scroll_irq.py` fails on it).
- **Cross-origin script requests send `Origin`** (okai `req_fetch`, `q->cors`). Servers echo Access-Control-Allow-Origin only for it; without it BBC's sign-in check failed and its script bounced bbc.com <-> bbc.co.uk forever (679 fetches).

## Architecture in 30 seconds

1. GRUB loads kernel at 1MB, provides multiboot info (memory map + framebuffer address)
2. `start.asm` LOW `_start` (e_entry, paging OFF) builds boot PD → `_start_high` sets up high stack, calls `kernel_main()`
3. `kernel_main()` does: GDT (kernel + user segments + TSS) → IDT (exceptions + IRQs + INT 0x80) → memory → paging → process table → graphics → windows → mouse → keyboard → networking → sti → main loop
4. Main loop: handle mouse clicks/drags → `okai_poll()` (fetches, sub-resources, coalesced page renders) → check JS rerender → draw windows (+ okai chrome overlay) → draw cursor → flush dirty rows
5. Keyboard/mouse work via hardware interrupts (IRQ1/IRQ12), not polling
6. Page scripts, stylesheets and images are fetched in parallel (keep-alive connection pool, `fetch_poll()` from the main loop) after the document parses; scripts run in the document's ojs realm (`okai_poll` pumps it under a time budget)

## Adding new features

- **New shell command:** add to `shell_execute()` in `desktop.c` (desktop) or `shell.c` (text). Follow the `str_eq(cmd_buf, "name")` pattern.
- **New window type:** use `window_create()`, `window_puts()`, `window_set_close_button()`. Windows auto-manage content buffers.
- **New interrupt handler:** add ISR stub in `isr.asm` (use `ISR_NOERRCODE`/`ISR_ERRCODE` macros), register in `idt_init()` in `idt.c`, add handler function.
- **New drawing primitive:** add to `graphics.c`, write to `backbuffer[]`, mark dirty rows with `graphics_mark_dirty(y)`.
- **New Web API:** prefer plain JS in `src/web/wjs_prelude.js` (rebuilt into `wjs_prelude.o`); add a C native in `wjs_dom.c` (exposed on the `W` object) only when it needs engine internals (DOM arena, layout, CSS). Test on the host first: `build-host/wbrowse <url|file> ...` (`tests/web/js/basic.html` must stay ALLPASS).
- **New process feature:** extend `process.c` (process_create/destroy/switch), update `process.h` with new fields.

## Text vs Desktop mode

The Makefile builds completely separate binaries from different source sets:
- Text: `kernel.c` + `vga.c` + `terminal.c` + `shell.c`
- Desktop: `desktop.c` + `graphics.c` + `window.c` + `paging.c` + `filesystem.c` + `editor.c` + `textslot.c` + `okai.c` + `web/*` + `ojs/*` + `net/*` + `crypto/*` + `string.c` + `theme.h`

Shared: `gdt.c`, `idt.c`, `memory.c`, `serial.c`, `keyboard.c`, `mouse.c`, `io.h`

If you modify shared code, test both builds. If you modify mode-specific code, only that build is affected. Networking, TLS, the web engine, ojs, and okai are desktop-only.

## Headless testing (okvm)

`tests/headless/okvm.py` drives QEMU headlessly for automated testing. Output goes to `~/okvm/`.

```python
import sys, time; sys.path.insert(0, 'tests/headless')
from okvm import OkVM
vm = OkVM("tag")
vm.wait_for("[mem] heap", timeout=40); time.sleep(10)
vm.type_string("okai\n")              # internal home page (no network)
vm.wait_for("home rendered", timeout=30)
vm.click_link("example.com")         # closed loop on [okai] click x=.. y=..
ok = vm.wait_for("parse: count=", timeout=70)
vm.kill()
```

Key facts:
- Serial log (`~/okvm/<tag>_serial.log`) is ground truth — never guess from pixels
- Mouse is RELATIVE and applied 1:1 (no smoothing since 2026-10-08) — `vm.burst(dx, dy, n)` moves ~n*(dx,dy)

Link targets come from `[okai] link[i] x= y= w= h= href=` (each page's first render; `vm.link_regions()`).
- `vm.wait_for(pattern)` matches ANY earlier occurrence — for "the next page loaded" count `parse: count=` lines instead

- **Network statistics + TCP loss recovery (2026-10-16; `net_stats_tick` in network.c, `e1000_take_stats`, `tcp_sack_blocks`).** Once a second, when anything moved, the serial log gets `[net] rx KB (pkts) tx KB (pkts) | tcp in KB rto fast ooo ooo-full ring-full | unread KB (max) socks fetch | nic max-batch missed nobuf poll-gap`: `unread` = bytes sitting in the receive rings (high = the application, i.e. JS/fetch, is the bottleneck, not the network), `poll-gap` = the longest time between two e1000 polls (a late poll lets the 256-entry ring fill and the card drop packets: `missed`/`nobuf` are its own counters), `ooo-full` = segments thrown away because no out-of-order slot was free. Together with `[vidfps]` (`buf` = seconds buffered ahead) this separates "the network is slow" (arrival KB/s low, `buf` near 0) from "we cannot keep up" (`buf` high, `unread` high). TCP receive side: window scaling (RFC 7323), 64 out-of-order slots per connection (was 8), SACK (RFC 2018: SACK-permitted in the SYN, blocks in duplicate ACKs, newest range first) - with `netdrop 100` (1% injected loss, loopback) an 8 MB download went 29 -> 76 Mbit/s and `ooo-full` drops disappeared. NOTE: with QEMU's user-mode networking the guest's TCP never sees the internet's loss (SLIRP terminates the connection and the virtual link is clean), so these help real NICs/Wi-Fi; a slow internet shows up as slow arrival, not as loss. Test page: `build-host/www/dl.html` (8 MB fetch with throughput printed), `-PreCmd "netdrop N"` in perf_win.ps1.

- **DNS over HTTPS (2026-10-17; `doh_*` in network.c, shell `doh [on|off]`).** Plain UDP DNS to the host's resolver was lied to by the user's network (NXDOMAIN for youtube.com only). Every lookup now goes through RFC 8484 GET requests (`/dns-query?dns=<base64url>`) on the fetch engine: cloudflare-dns.com (1.1.1.1), then dns.google (8.8.8.8), then dns.quad9.net (9.9.9.9), then plain UDP. The three names resolve from a built-in table (`doh_bootstrap`), the certificate is checked against the name. Per-lookup state: `method`, `doh_state`, `doh_h` in `struct dns_ent`; `doh_step` runs from `dns_poll`; 3.5 s per server, 2 s waiting for a free fetch slot; two failures in a row switch DoH off for 60 s (no Internet = no 6 s penalty per lookup). An NXDOMAIN from DoH is an answer, not a failure. Log lines `[dns] querying 'x' (DoH ...)`, `[dns] DoH works`, `[dns] DoH ... : why`. `perf_win.ps1 -NetDev "user,id=net0,restrict=on"` tests the fallback (DoH fails at once, UDP takes over); `-PreCmd "doh off"` tests the UDP path.
- **Main-loop stalls on page loads: found, mostly fixed (2026-10-17; `stall_sample` in prof.c, `tools/stallsym.py`, `heap_pretouch`, `tools/media/p720y.html`).** Symptom (user): YouTube video freezes, drops 8-32 frames/s, sound underruns during the first ~25 s of every watch page. Method: `prof on` now also runs a STALL SAMPLER - the main loop and the media service stamp `stall_beat`; the timer IRQ (isr.asm saves the interrupted EIP/CS/ESP in `irq_last_*`), finding the stamp older than 100 ms while the loop is not halted, records EIP + the first two kernel-code words near the top of the stack (the caller of a leaf like memset); the loop prints `[stall] N ms (M samples): eip<caller,caller2>*count` when it comes back and `python3 tools/stallsym.py kanarchy-desktop.bin perf.log` resolves them with nm. Repro without YouTube login: `tools/media/p720y.html` (a local 720p60 clip + a YouTube iframe; copy it next to `v720.webm` in `build-host/www`, serve with `python3 -m http.server 8005`, `perf_win.ps1 -Smp 4 -Mem 1536 -Prof -StampVid -AudioWav <abs path> -Urls http://10.0.2.2:8005/p720y.html`; NOTE: pass the WAV path with a literal Windows path, `$env:TEMP` inside a bash call expands to nothing and then the sound card has no output and the media clock never runs). Findings: (1) **the first write to a page of guest RAM costs ~70,000 cycles (19 us) under WHPX** (shell `memtouch [MB]`: 46 cycles for the second write; QEMU's `prealloc=on` does not help, it is the EPT mapping), so a JS heap growing by 170 MB stalled the loop for up to 3 s inside memset/gc_alloc/kmalloc. `heap_pretouch` (memory.c) writes a lock-prefixed `add 0` to every heap page ahead of the allocator (kmalloc carves from the low end) in the idle path of the main loop (6 ms per pass when fully idle, 0.3 ms per packet-poll sleep); log `[mem] heap pre-touched`. (2) the 20 ms media hook (`wjs_media_tick`) only served the realm that was running a script: a script in an iframe froze a video in the parent. It now serves every realm that owns media sessions (`media_realms[]`). (3) GC marking (`drain` in gc.c) and parsing (`arena_alloc` in parse.c) call the host interrupt hook (result ignored), so a 200 ms GC or a 1 s parse keeps the sound card fed. (4) decode pipeline: `VW_RING` 12, `VW_BATCH` 8, `VW_AHEAD_NS` 150 ms (the worker was only allowed to decode 60 ms ahead and 3 frames per submission: throughput was capped by how often the busy main loop polled). Result on the repro: longest gap 3430 -> ~180 ms, underruns 10 -> 0, drops during the load roughly halved (load phase still 40-45 shown fps of 60, steady state 60). Remaining stall sources are layout/style/paint (no hook yet) and GC itself.
- **The kernel clock follows the TSC (2026-10-17; `on_timer`/`timekeeping_init` in desktop.c, `cpufreq_tsc_reliable`).** The user's `[vidfps]` showed the media clock (sound card position) at 1.18 s per kernel second: QEMU on Windows loses ~15% of its PIT interrupts, so `tick_count` (Date.now(), timers, timeouts, the taskbar clock) ran slow. `tick_count = max(delivered PIT ticks, TSC-derived ticks)`; the TSC is only used under a hypervisor or with CPUID invariant TSC. `[time] N of M ticks were not delivered` every 10 s when more than 20 were lost; shell `tickdrop N` loses every Nth interrupt on purpose (test: `perf_win.ps1 -PreCmd "tickdrop 6" -StampVid`: rtc keeps pace with wall time). `[vidfps]` has `rtc` (tick seconds) and `tsc` (ms from the cycle counter) next to `clock` (media ms): compare them to see which clock is wrong.
- **QEMU's PIT is coarse under Windows: the kernel tick runs 35-40% slow when idle (2026-10-17).** Measured with the `[time]` line (`perf_win.ps1 -Urls https://example.com/`): 37-40% of the 100 Hz PIT interrupts are never delivered on an idle desktop (the vCPU sleeps in `hlt`, QEMU's user-space PIT is woken by a host timer of ~15.6 ms: ~64 Hz), 15% on the user's machine, ~0% while the vCPU is busy. The LAPIC one-shot timer (used for the 0.5 ms network sleeps) is NOT affected (a 500 us sleep takes 498 us under WHPX: hypervisor-side). `tick_count` now follows the TSC (see the previous bullet), so Date.now(), timers and timeouts are real time. Anything that counts timer INTERRUPTS instead of reading `tick_count` (the sched slice, `audio_tick`) still runs at the lost rate.
- **QEMU's HD Audio model on a Windows host: the card's position is a lie; use AC'97 (2026-10-17; `src/ac97.c/.h`, `src/audio_rate.c/.h`, host test `tests/test_arate.c`, `tools/media/loopback_tone.ps1`, shell `audiorate [pct]` / `audiotrace` / `audiotest`).** Symptom (user): YouTube sound too fast / later (after a first fix) too slow and pitched down, plus stutters, video unable to keep up with the clock. Measured: the kernel compares the card's position (HDA LPIB) with the TSC every 3 s: with `run-windows.bat`'s old `-device intel-hda` it ran at **1.00-1.24x real time, differing from run to run on the same host/config** (1.19 on the user's machine every time). QEMU's HDA output (`hw/audio/hda-codec.c`) is TIMER-driven: a virtual-clock timer (1 ms ticks, coarse under Windows) DMA-reads the guest buffer into an 8 KB (42 ms) buffer at the nominal rate and a small PLL (`hda_timer_sync_adjust`) moves its time base by 1 or 4 ms whenever the audio core's callback finds that buffer low; when the buffer overruns it DROPS the whole 42 ms. So LPIB advances in bursts (3-4 ticks at ~1.4x, then nothing - `audiotrace` + the awk in the log shows it) and about 4.5 times a second 42 ms of sound is thrown away; what is actually played is the stream at the right pitch but with holes and a timeline that follows LPIB. Proof from outside the guest: `tools/media/loopback_tone.ps1` records the Windows output (WASAPI loopback) while okai plays a -40 dB 19.4 kHz tone (`ffmpeg -f lavfi -i sine=frequency=19377,volume=-40dB`; ultrasonic so a user's own music does not drown it), then reports the pitch and counts phase jumps: unstretched HDA = exact pitch with ~9 jumps per 2 s; with the 1.19x resampling that was in this tree for a day the pitch came out 0.84x (the user's "slowed down") and still had the holes (500+ jumps per 2 s), i.e. the correction made it worse - the position of an emulated card is not the audible speed. **Fixes:** (1) `run-windows.bat` now uses `-device AC97,audiodev=snd0` with `in.voices=0` (SDL refuses AC'97's input voices without a microphone: "Could not create a backend" lines at start are harmless): QEMU's AC'97 (`hw/audio/ac97.c`) is pull-driven (takes exactly what the backend accepts, no timer, no PLL, no drops): position 0.998-0.999x real, phase jumps ~0. `src/ac97.c` is a polled driver for the ICH PCM-out engine (32 buffer descriptors over the same 512 KB ring `hda.c` uses, LVI kept one buffer behind CIV by `ac97_tick`, position = CIV * buffer + consumed part of the current buffer from PICB); `audio_init` tries HD Audio first and falls back to AC'97 (only when a class 4.1 device exists: an unconditional allocation of the 512 KB ring made `test_okai_media.py` fail on machines without any sound card). Headless: `OKVM_AUDIO_CARD=ac97` (okvm.py), `perf_win.ps1 -AudioCard ac97`. (2) the speed measurement stays but is OBSERVE-ONLY for the drivers (`struct arate.observe_only`, `measured_q16`; the log line says "not corrected"); `audiorate 118` still forces a stretch for experiments. (3) `audio_clock()` is smoothed (`aclk_smooth`: runs at TSC real time, pulled toward the card with a 250 ms time constant, never backwards, never > 20 ms ahead; tested against a bursty position: worst error 471 frames from real time where the raw position is 912 off, 10 ms steps within 10 frames): the burst pattern made a 24 fps picture show frames at irregular 60-90 ms intervals. Not tried / unknown: a bad-host-state HDA run is still wrong in QEMU (use AC'97); real HDA hardware is untouched. Harness notes: `perf_win.ps1 -AudioDev "<audiodev string>"` swaps the backend; SDL's `dummy` driver (`SDL_AUDIODRIVER=dummy`) is silent but runs at 0.88x (SDL_Delay quantisation), useless for speed.
